# ระบบวิเคราะห์ความคุ้มค่าครุภัณฑ์ทางการแพทย์ (Medical Equipment Utility Analysis)

Web Application สำหรับให้โรงพยาบาลบันทึกข้อมูลการใช้งาน ต้นทุน และผลลัพธ์ของครุภัณฑ์รายปี
คำนวณ Utility Score ตามชุดสูตรที่อนุมัติ (v1.0) และแสดงผลประกอบการตัดสินใจของผู้บริหาร

- เอกสารวิเคราะห์และออกแบบ: [`docs/Phase1-Analysis-Design.md`](docs/Phase1-Analysis-Design.md)
- ภาพ Mockup: [`docs/mockups/`](docs/mockups)

> ข้อมูลในระบบสำหรับพัฒนาเป็นข้อมูลตัวอย่าง (DEMO) ทั้งหมด ไม่ใช่ข้อมูลจริงของหน่วยงาน

## โครงสร้าง

```
packages/formula   ชุดสูตร Utility Score v1.0 (Pure TypeScript) + Golden Test เทียบกับค่าใน Excel
apps/api           Backend: Fastify + PostgreSQL (Row-Level Security แยกข้อมูลแต่ละโรงพยาบาล)
  migrations/      SQL migration
  scripts/         migrate.ts, seed-dev.ts (ข้อมูล DEMO)
  test/            Integration test กับ PostgreSQL จริง
apps/web           Frontend: React + Vite (ภาษาไทย, Responsive)
e2e/smoke.cjs      ทดสอบผ่านเบราว์เซอร์ (Playwright)
docs/              เอกสารวิเคราะห์ ออกแบบ และ Mockup
```

**เทคโนโลยี:** TypeScript ทั้งระบบ เพื่อใช้ชุดสูตรเดียวกันทั้งหน้าเว็บและ Server · Backend ใช้ Fastify 5 แทน NestJS ที่เสนอไว้ในเอกสารแผนพัฒนา (ข้อ 4.1) เพราะโค้ดน้อยกว่าและดูแลง่ายกว่าสำหรับขนาดระบบนี้ · ฐานข้อมูลใช้ SQL ตรงผ่าน `pg` (ไม่ใช้ ORM) เพื่อควบคุม Row-Level Security ได้เต็มที่

## เริ่มใช้งานใน VS Code

สิ่งที่ต้องมี: Node.js 20 ขึ้นไป, Docker Desktop (หรือ PostgreSQL 16)

1. เปิดโฟลเดอร์โปรเจกต์ใน VS Code แล้วติดตั้ง Extension ที่ระบบแนะนำ
2. เปิดฐานข้อมูล:

```bash
docker compose up -d
```

3. ติดตั้ง package:

```bash
npm install
```

4. สร้างไฟล์ตั้งค่า API:

```bash
cp apps/api/.env.example apps/api/.env
```

5. สร้างตารางและบัญชีแอป (อ่านค่าจาก `apps/api/.env`):

```bash
npm run db:migrate
```

6. ใส่ข้อมูลตัวอย่าง (DEMO):

```bash
npm run db:seed
```

ถ้าต้องการข้อมูลรายปีตัวอย่างที่ยืนยันแล้ว (ปีงบ 2565–2568) เพื่อดูหน้าผลวิเคราะห์ ให้ใช้คำสั่งนี้แทน:

```bash
npm run db:seed -- --annual
```

7. เปิดระบบ: ใน VS Code ไปที่ **Run and Debug** แล้วเลือก **API + Web** หรือรัน 2 คำสั่งนี้ใน Terminal แยกกัน:

```bash
npm run dev:api
```

```bash
npm run dev:web
```

8. เปิด http://localhost:5173 แล้วเลือกบัญชีตัวอย่างในกล่อง "โหมดพัฒนา"

| บัญชีตัวอย่าง | บทบาท |
|---|---|
| `PID-DEMO-A-ENTRY` | เจ้าหน้าที่บันทึกข้อมูล รพ.ตัวอย่าง A |
| `PID-DEMO-A-ADMIN` | ผู้ดูแลระบบ รพ.ตัวอย่าง A |
| `PID-DEMO-A-REVIEW` | ผู้ตรวจสอบ รพ.ตัวอย่าง A |
| `PID-DEMO-A-EXEC` | ผู้บริหาร รพ.ตัวอย่าง A |
| `PID-DEMO-B-ENTRY` | เจ้าหน้าที่บันทึกข้อมูล รพ.ตัวอย่าง B |
| `PID-DEMO-CA` | ผู้ดูแลระบบส่วนกลาง |
| `PID-DEMO-CE` | ผู้บริหารส่วนกลาง (ดูได้ทุกโรงพยาบาล) |

## หลักการสำคัญที่ระบบบังคับใช้

- **สูตรตรงกับ Excel:** `packages/formula` ถอดสูตรจากชีต "ข้อมูลครุภัณฑ์" ตรงตัว และทดสอบเทียบกับค่าที่ Excel คำนวณไว้ 8 แถว ห้ามแก้สูตรโดยไม่สร้างเวอร์ชันใหม่
- **ข้อมูลไม่ครบไม่ได้คะแนน (D-08):** ระบบไม่คำนวณ และบอกว่าขาดข้อมูลอะไร
- **แยกข้อมูลรายโรงพยาบาล 2 ชั้น:** API กรองตามโรงพยาบาลของผู้ใช้ และ PostgreSQL Row-Level Security กันซ้ำ แอปเชื่อมต่อด้วยบัญชี `mu_app` ที่ไม่ใช่ owner
- **Audit Log แก้ไม่ได้:** เพิ่มได้อย่างเดียว (trigger + สิทธิ์) และมี hash chain ตรวจการแก้ไขย้อนหลังได้ที่ `GET /api/audit/verify`
- **ไม่เก็บรหัสผ่าน:** session เก็บเฉพาะ hash ของ token, cookie เป็น HttpOnly + SameSite=Strict, คำขอที่เปลี่ยนข้อมูลต้องมี header `x-mu-csrf`
- **แก้ไขพร้อมกัน:** ใช้ version ป้องกันการบันทึกทับข้อมูลที่ผู้อื่นเพิ่งแก้
- **ข้อมูลรายปีแยกแต่ละปี:** 1 แถวต่อครุภัณฑ์ต่อปีงบ แก้ได้เฉพาะตอนเป็นร่าง ส่งตรวจแล้วต้องให้ผู้ดูแล รพ. ปลดล็อก (ระบุเหตุผล) ทุกขั้นตอนบันทึกในประวัติการตรวจสอบและ Audit Log
- **แยกหน้าที่ (Segregation of Duties):** ผู้ที่บันทึกหรือแก้ไขข้อมูลยืนยันข้อมูลนั้นเองไม่ได้
- **ส่งตรวจได้เมื่อข้อมูลครบ:** ระบบตรวจช่องบังคับและความสัมพันธ์ เช่น วันใช้จริง ≤ วันพร้อมใช้ และถ้าค่าเปลี่ยนจากปีก่อนมาก (Utilization ±30 จุด, ค่าบำรุงรักษา ±30%) ต้องระบุเหตุผล

## Dashboard (Sprint 5)

- **Dashboard โรงพยาบาล** (หน้าแรกของผู้ใช้โรงพยาบาล): KPI 6 ตัว, กราฟ 6 กราฟ (Score รายครุภัณฑ์, เรดาร์ 6 ปัจจัย, Utilization/ค่าบำรุงรักษา/Downtime ย้อนหลัง 5 ปี, รายได้เทียบค่าบำรุงรักษา), ตารางจัดอันดับ และตัวกรอง 6 แบบ (ปีงบ, หน่วยงาน, ประเภท, ชื่อ, ช่วงราคา, ระดับคะแนน)
- **Dashboard ภาพรวมเครือข่าย** (หน้าแรกของผู้ใช้ส่วนกลาง): สรุปรายโรงพยาบาล ความคืบหน้ารอบประเมิน การกระจายระดับคะแนน ตาราง "แต่ละโรงพยาบาลมีข้อมูลแบบไหน" 3 ชุด (ประเภทครุภัณฑ์, ความครบถ้วนแต่ละหมวด, ข้อมูลย้อนหลังที่มี) และสิ่งที่ควรติดตาม
- **หน้ารายละเอียดครุภัณฑ์**: กราฟแนวโน้ม 4 กราฟ
- ตัวเลขทุกตัวมาจากข้อมูลที่ยืนยันแล้วเท่านั้น · Utilization/Downtime รวมแบบถ่วงน้ำหนักด้วยชั่วโมง · ปีที่ไม่มีข้อมูลแสดงเป็นช่องว่าง ไม่แสดงเป็น 0

## การคำนวณ Utility Score (Sprint 4)

- ใช้ชุดสูตรที่อนุมัติล่าสุดในฐานข้อมูล (ปัจจุบัน **v1.1**) และแสดงเวอร์ชันสูตรทุกหน้า
- ปีวิเคราะห์ Y ใช้เฉพาะข้อมูลรายปีที่ **ยืนยันหรือล็อกแล้ว** ในปีงบ Y−4 ถึง Y รวมเป็นค่าสะสมตาม D-02 แล้วคำนวณด้วยสูตร Excel
- ไม่มีข้อมูลที่ยืนยัน หรือข้อมูลไม่ครบ → **ไม่ให้คะแนน** และแสดงเหตุผล
- อันดับ (RANK) คิดภายในแต่ละโรงพยาบาล
- ทุกคะแนนกดดู **ที่มาของคะแนน** ได้: คะแนนแต่ละปัจจัย × น้ำหนัก, สูตรพร้อมตัวเลขจริง, ปีงบที่ใช้
- **ปิดรอบประเมิน** แล้วระบบบันทึกผล ณ วันนั้น (snapshot ข้อมูลที่ใช้ + เวอร์ชันสูตร) เป็นประวัติการประเมิน

## ขั้นตอนรอบการประเมิน (Sprint 3)

1. **ผู้ดูแล รพ.** เปิดรอบปีงบที่เพิ่งสิ้นสุด (ค่าเริ่มต้นเปิดรับ 1–31 ต.ค.) ระบบสร้างรายการครบกำหนดจากครุภัณฑ์ที่ใช้งาน/พร้อมใช้/ซ่อม พร้อมเหตุเพิ่ม (ครบอายุใช้งาน, รับเข้าใหม่) แล้วมอบหมายเจ้าหน้าที่
2. **เจ้าหน้าที่** ตรวจสภาพเครื่อง กรอกข้อมูล 4 หมวด บันทึกประวัติซ่อมบำรุง แล้วส่งตรวจ
3. **ผู้ตรวจสอบ** ยืนยัน หรือตีกลับพร้อมเหตุผล (เจ้าหน้าที่เห็นเหตุผลในรายการครบกำหนด)
4. **ผู้ดูแล รพ.** ปิดรอบ ข้อมูลที่ยืนยันแล้วถูกล็อก

ข้อมูลปีย้อนหลัง (D-15) บันทึกได้จากหน้ารายละเอียดครุภัณฑ์ → ตาราง "ข้อมูลรายปี" ซึ่งใช้แบบฟอร์มและขั้นตอนยืนยันเดียวกัน · เหตุ "ครบกำหนดสอบเทียบ" ยังไม่สร้างอัตโนมัติ เพราะทะเบียนยังไม่มีช่องกำหนดวันสอบเทียบ
